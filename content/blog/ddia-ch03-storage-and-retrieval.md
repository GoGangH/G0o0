DB에 값을 저장하고 다시 읽는 일은 API로 보면 단순합니다. 그런데 내부로 들어가면 같은 값을 저장하는 방법이 꽤 다릅니다.

파일 끝에 계속 붙일 수도 있고, 기존 페이지를 찾아 바꿀 수도 있습니다. 인덱스를 추가하면 읽기는 편해지지만, 쓸 때 해야 할 일이 늘어납니다.

3장은 이 차이를 설명합니다. **쓰기를 빨리 끝냈다면, 뒤에서 어떤 일을 더 해야 하는가.** 이 질문을 기준으로 정리했습니다. 장 번호는 DDIA 1판 기준입니다.

## 파일 끝에 붙이면 쓰기는 쉽다

가장 단순한 저장소를 생각해 봤습니다. 키와 값을 파일 끝에 계속 추가합니다.

```text
user:7,민수
user:9,지수
user:7,강현
```

`user:7`의 현재 값은 마지막에 쓴 `강현`입니다. 기존 값을 찾아서 덮어쓸 필요가 없으니 쓰기는 단순합니다. 대신 읽을 때는 어느 위치가 최신인지 알아야 합니다.

전체 파일을 매번 훑는 대신, 메모리에 `키 → 최신 레코드의 위치`를 저장하면 됩니다. 이것이 해시 인덱스의 출발점입니다.

다만 키가 많아지면 인덱스도 커지고, 키 순서가 없으니 범위 조회에는 맞지 않습니다. `user:100`부터 `user:200`까지 읽고 싶어도 해시만으로는 이웃 키를 찾을 수 없습니다.

오래된 값도 계속 남습니다. 세그먼트를 나누고, 같은 키의 낡은 버전을 정리하는 **컴팩션**이 필요해집니다. 쓰기를 간단하게 만든 만큼 읽기와 정리 과정에 일이 생긴 것입니다.

## SSTable은 무엇이 다른가

SSTable은 키 순서로 정렬된 파일입니다. 위 로그와 달리 정렬되어 있다는 점이 중요합니다.

모든 키의 위치를 메모리에 올릴 필요가 없습니다. 블록의 시작 키와 위치 정도만 알아도, 찾는 키가 들어갈 블록을 고른 뒤 그 안에서 찾을 수 있습니다. 정렬된 파일끼리는 병합도 쉽습니다.

문제는 들어오는 쓰기를 매번 디스크 위에서 정렬하기 어렵다는 것입니다. 그래서 메모리에 정렬된 자료구조인 **멤테이블**을 두고, 일정 크기가 되면 SSTable로 내보냅니다.

![쓰기 요청을 WAL과 멤테이블에 기록하고 SSTable로 내보낸 뒤 컴팩션하는 과정](/blog/ddia-ch03-storage-and-retrieval/lsm-write-path.svg)

그림은 일반적인 LSM 계열의 흐름을 단순화한 것입니다. WAL 기록과 멤테이블 갱신을 거쳐 쓰기를 처리하고, 멤테이블이 차면 파일로 내보냅니다. 응답 전에 WAL을 영구 저장까지 기다리는지는 동기화 설정과 내구성 정책에 따라 달라집니다.

LevelDB도 로그, 멤테이블, 정렬된 테이블 파일을 함께 사용합니다. 구체적인 파일 구성은 [LevelDB 구현 문서](https://github.com/google/leveldb/blob/main/doc/impl.md)에서 확인할 수 있습니다.

## 메모리에 썼는데 장애가 나면 어떻게 되는가

멤테이블은 메모리입니다. SSTable로 내보내기 전에 프로세스가 죽으면 그 안의 데이터는 사라집니다.

그래서 복구용 로그인 **WAL**이 필요합니다. 재시작하면 남아 있는 로그를 재생해서 아직 파일로 내보내지 못한 상태를 복구합니다. 단, 로그를 썼다는 것과 디스크에 영구 반영했다는 것은 다릅니다. OS 버퍼에만 남아 있던 기록은 전원 장애 때 잃을 수 있습니다.

여기서 로그라는 이름도 구분해야 합니다. 앞에서 본 단순 저장소의 로그는 그 자체가 데이터를 담는 주 저장 구조였습니다. WAL은 장애 복구를 위해 변경 내용을 먼저 남기는 기록입니다.

B 트리도 WAL을 사용할 수 있습니다. WAL은 LSM만의 특징이 아닙니다. [PostgreSQL의 WAL 설명](https://www.postgresql.org/docs/current/wal-intro.html)도 데이터 페이지보다 로그를 먼저 영구 저장해야 한다는 원칙을 설명합니다.

## 정렬된 파일이 여러 개면 어디부터 읽는가

같은 키가 멤테이블과 여러 SSTable에 있을 수 있습니다. 조회할 때는 최신 상태를 찾아야 합니다. 단순화하면 메모리와 최신 파일부터 확인하고, 없으면 더 오래된 파일을 확인하는 방식입니다. 실제 엔진은 레벨, 키 범위, 시퀀스 번호 등을 이용해 탐색 대상을 줄입니다.

파일이 쌓이면 읽을 곳도 늘어납니다. 컴팩션은 정렬된 파일들을 병합하면서 불필요해진 옛 버전을 정리합니다. 이 구조가 LSM 트리로 이어집니다.

삭제도 바로 모든 파일에서 키를 지우는 식으로 처리하기 어렵습니다. 삭제 표시인 **툼스톤**을 써두고, 조회할 때 과거 값이 다시 보이지 않게 합니다. 툼스톤은 더 오래된 값을 가릴 필요가 없고 진행 중인 스냅샷에도 필요하지 않은 등, 안전하게 제거할 수 있을 때 정리해야 합니다.

존재하지 않는 키를 찾는 비용은 블룸 필터로 줄일 수 있습니다. 블룸 필터가 “없다”고 하면 그 파일은 건너뜁니다. “있을 수 있다”고 하면 실제로 확인해야 합니다. **없는데 있다고 판단하는 경우는 있지만, 정상적으로 구성된 필터가 있는 키를 없다고 하지는 않습니다.**

## 순차 쓰기인데 왜 쓰기 증폭이 생기는가

파일 끝에 순서대로 쓰는 것과, 디스크에 쓰는 총량이 적다는 것은 다른 이야기입니다.

사용자가 쓴 데이터가 WAL에 기록되고, SSTable로 내보내지고, 컴팩션 과정에서 다시 쓰일 수 있습니다. 애플리케이션이 전달한 양보다 저장 장치가 더 많은 데이터를 쓰는 현상이 **쓰기 증폭**입니다.

읽기 증폭은 하나의 요청을 처리하려고 여러 파일이나 블록을 확인하는 비용이고, 공간 증폭은 옛 버전과 정리 중인 파일 등으로 실제 데이터보다 공간을 더 쓰는 비용입니다.

LSM은 이 세 가지를 함께 조절합니다. 컴팩션을 자주 하면 읽기와 공간에는 도움이 될 수 있지만 다시 쓰는 양이 늘어납니다. 미루면 당장 쓰기는 편해도 파일이 쌓입니다. [RocksDB의 컴팩션 문서](https://github.com/facebook/rocksdb/wiki/Compaction)에서도 전략에 따라 이 비용의 비중이 달라집니다.

그래서 “LSM이면 쓰기가 무조건 빠르다”까지 가면 곤란합니다. 컴팩션이 유입되는 쓰기를 따라가지 못하면 쓰기가 지연되거나 멈출 수 있습니다.

## B 트리는 어떤 비용을 선택하는가

B 트리는 데이터를 고정 크기 페이지로 나누고, 키 범위를 따라 필요한 페이지를 찾습니다. 기존 키를 갱신할 때는 해당 페이지를 메모리에서 바꾸고 나중에 디스크에 반영합니다. 페이지가 차면 분할이 필요할 수 있습니다.

보통 DB에서 말하는 B 트리 인덱스는 B+ 트리 계열입니다. 내부 페이지는 탐색 경로를 제공하고, 리프에 키와 값 또는 레코드를 찾을 위치가 있습니다. 리프 연결을 이용하면 범위 조회도 이어갈 수 있습니다.

![LSM은 정렬 파일을 병합하고 B 트리는 키 범위에 해당하는 페이지를 갱신하는 구조 비교](/blog/ddia-ch03-storage-and-retrieval/lsm-vs-btree.svg)

| 관점 | LSM 계열 | B 트리 계열 |
| --- | --- | --- |
| 쓰기 흐름 | 메모리에 모으고 정렬 파일로 내보낸 뒤 병합 | 대상 페이지를 찾아 갱신, 필요하면 분할 |
| 읽기 흐름 | 여러 버전과 파일 중 유효한 값 탐색 | 트리 경로를 따라 대상 리프 탐색 |
| 뒤에서 생기는 일 | 컴팩션, 옛 버전 정리 | 변경 페이지 반영, 페이지 관리 |
| 확인할 비용 | 컴팩션 I/O, 읽기·쓰기·공간 증폭 | WAL, 페이지 쓰기, 분할과 공간 사용 |

어느 쪽도 디스크 I/O가 공짜는 아닙니다. 실제 성능은 캐시 적중률, 값 크기, 조회 범위, 동기화 설정까지 같이 봐야 합니다. 이 비교는 구조의 차이를 보기 위한 것이고, 특정 DB의 성능 순위는 아닙니다.

## 인덱스를 추가하면 왜 쓰기가 느려지는가

인덱스도 별도로 유지해야 하는 자료구조입니다. 보조 인덱스가 세 개라면 데이터 하나를 바꾸면서 관련 인덱스들도 갱신해야 할 수 있습니다.

인덱스를 타더라도 원하는 열이 전부 들어 있지 않으면 실제 레코드를 추가로 읽어야 합니다. 반대로 필요한 열을 인덱스에 담으면 조회를 줄일 여지가 있지만, 인덱스 크기와 갱신 비용이 늘어납니다.

복합 인덱스도 순서가 중요합니다. `(game_id, finished_at)`은 먼저 게임별로 묶고 그 안에서 종료 시각 순으로 정렬한 구조입니다. 특정 게임의 기간별 기록에는 자연스럽지만, 모든 게임의 종료 시각만으로 찾는 요청에는 같은 이점을 기대하기 어렵습니다.

결국 인덱스를 추가한다는 것은 **읽을 때 할 일을 쓰는 쪽으로 옮기는 선택**입니다.

## 분석 쿼리에서는 저장 방향도 달라진다

OLTP는 특정 사용자나 거래처럼 적은 레코드를 읽고 자주 바꾸는 요청이 많습니다. OLAP는 많은 레코드에서 일부 열을 읽고 집계하는 요청이 많습니다. 웨어하우스는 보통 운영 데이터에서 ETL 등의 과정으로 분석용 데이터를 가져옵니다. 스타 스키마는 사건을 담는 사실 테이블과 사용자·상품 같은 차원 테이블로 이를 구성하는 한 방법입니다.

예를 들어 구매 이력 전체에서 `SUM(amount)`를 계산한다면, 사용자 이름과 배송지까지 같이 읽을 이유가 없습니다. 열 지향 저장은 같은 열의 값을 모아서 저장해 필요한 열 위주로 읽게 합니다. 비슷한 값이 모이므로 압축에도 유리합니다.

![동일한 데이터를 행 단위 또는 열 단위로 배치했을 때 amount 집계가 읽는 범위 비교](/blog/ddia-ch03-storage-and-retrieval/row-vs-column.svg)

그림은 배치 원리를 설명합니다. 실제 읽기 단위는 블록이고 압축이나 인덱스에도 영향을 받습니다. 분석 저장소는 비트맵 등으로 열을 압축하고, 벡터화 실행으로 여러 값을 한 번에 처리하기도 합니다. 반복되는 집계를 미리 계산해두는 방법도 있습니다. 대신 데이터가 바뀌면 미리 계산한 결과를 유지하는 비용이 생깁니다.

행 지향이 항상 느리거나 열 지향이 항상 빠른 것은 아닙니다. **한 행의 여러 값을 함께 읽는가, 많은 행의 일부 열을 읽는가**가 먼저입니다.

## 읽고 남은 기준

저장 엔진을 고를 때 자료구조 이름만 외우면 선택 이유가 흐려집니다. 다음 질문이 더 도움이 됐습니다.

- 한 키를 찾는 요청이 많은가, 범위 조회가 많은가.
- 쓰기를 받은 뒤 정리 작업이 계속 따라갈 수 있는가.
- 장애가 났을 때 어디까지 보존해야 하는가.
- 인덱스를 유지하는 비용보다 읽기를 줄이는 이득이 큰가.
- 한 레코드가 필요한가, 여러 레코드의 집계가 필요한가.

결국 3장은 읽기와 쓰기 사이에서 비용을 어디에 둘 것인지 설명하는 장으로 이해했습니다. 이어지는 [4장](/blog/ddia-ch04-encoding-and-evolution)에서는 그렇게 저장한 데이터를 코드가 바뀐 뒤에도 읽을 수 있는지 살펴봅니다.
