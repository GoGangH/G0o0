[3장](/blog/ddia-ch03-storage-and-retrieval)은 데이터를 어떻게 저장하고 읽는지 다뤘습니다. 4장은 코드가 바뀌어도 그 데이터를 읽을 수 있는지 다룹니다. 장 번호는 DDIA 1판 기준입니다.

서버 코드는 배포하면 바뀝니다. 하지만 DB에 저장한 값, 큐에 쌓인 메시지, 사용자가 아직 업데이트하지 않은 앱은 그대로 남습니다.

**새 코드와 예전 데이터가 만나고, 예전 코드와 새 데이터도 만납니다.** 이 상황을 버틸 수 있게 만드는 것이 이 장의 핵심입니다.

## 인코딩은 메모리 밖으로 나가는 형식이다

프로세스 안에서는 객체를 쓰면 됩니다. 하지만 파일에 저장하거나 네트워크로 보내려면 바이트로 바꿔야 합니다. 이 과정이 인코딩이고, 다시 객체로 읽는 것이 디코딩입니다.

언어에 내장된 객체 직렬화는 편합니다. 대신 언어와 클래스 구조에 묶이기 쉽고, 오래된 데이터를 읽기 어려워질 수 있습니다. 일부 형식은 신뢰할 수 없는 데이터를 역직렬화할 때 보안 문제도 생깁니다.

그래서 데이터가 오래 남거나 다른 서비스로 넘어간다면, 지금의 객체 구조보다 **읽고 쓰는 쪽이 공유할 형식**을 먼저 생각해야 합니다.

## 호환성은 두 방향으로 봐야 한다

| 방향 | 누가 무엇을 읽는가 | 필요한 상황 |
| --- | --- | --- |
| 하위 호환성 | 새 코드가 예전 데이터를 읽음 | 배포 뒤 기존 DB 레코드 조회 |
| 상위 호환성 | 예전 코드가 새 데이터를 읽음 | 순차 배포 중 구버전 서버가 새 메시지 처리 |

![하위 호환성은 새 리더가 옛 데이터를, 상위 호환성은 옛 리더가 새 데이터를 읽는 방향](/blog/ddia-ch04-encoding-and-evolution/compatibility.svg)

새 코드가 옛 데이터를 읽는 것은 개발할 때 확인하기 쉽습니다. 그런데 순차 배포에서는 한동안 구버전과 신버전 서버가 같이 뜹니다. 그때는 반대 방향도 필요합니다.

그리고 읽을 수 있다는 말도 나눠야 합니다. 파싱에 성공하는 것과 값의 의미를 올바르게 이해하는 것은 다릅니다. `amount`의 단위를 원에서 전으로 바꾸면 숫자 자체는 읽혀도 계산은 틀어집니다.

## JSON이면 스키마를 신경 쓰지 않아도 되는가

JSON은 읽기 쉽고 여러 언어에서 쓸 수 있습니다. 하지만 스키마를 파일로 선언하지 않았다고 약속이 없는 것은 아닙니다. 약속은 접근 코드와 검증 로직 안에 남습니다.

```json
{ "userId": "7", "name": "강현" }
```

여기에 `nickname`을 추가했을 때 구버전 코드가 모르는 필드를 무시하면 괜찮을 수 있습니다. 반대로 알 수 없는 필드를 오류로 처리하면 깨집니다. 필드 추가가 안전한지는 형식 이름만으로 결정되지 않습니다.

숫자 표현도 조심해야 합니다. JSON 자체와 별개로, JavaScript에서 숫자를 `number`로 읽으면 큰 정수를 정확하게 표현하지 못할 수 있습니다. ID나 금액을 어떤 타입과 단위로 전달할지 따로 정해야 합니다.

XML과 CSV도 자주 쓰는 텍스트 형식입니다. XML은 스키마로 제약을 표현할 수 있고, CSV는 단순한 표 교환에 편합니다. 다만 CSV는 열 이름과 타입, 이스케이프 규칙 등을 별도로 합의해야 합니다. 어떤 형식이든 바이트를 해석하는 규칙은 필요합니다.

## Protocol Buffers와 Thrift는 필드에 번호를 붙인다

JSON은 데이터에 필드 이름을 함께 적습니다. Protocol Buffers와 Thrift 같은 바이너리 형식은 필드 번호를 이용합니다. 세부 인코딩은 다르지만, 이름을 매번 기록하는 비용을 줄이고 번호로 필드를 식별한다는 점이 중요합니다.

```protobuf
// 구조를 설명하기 위한 proto3 예시입니다.
message User {
  string user_id = 1;
  string name = 2;
  optional string nickname = 3;
}
```

기존 코드가 모르는 필드를 건너뛸 수 있고, 새 코드는 예전 메시지에 없는 필드를 기본값이나 존재 여부를 고려해서 처리할 수 있습니다. 새 필드가 없을 때의 동작을 정해야 이 장점이 실제 호환성으로 이어집니다.

여기서 식별자는 `name`이라는 이름보다 `2`라는 번호입니다. 필드를 삭제한 뒤 그 번호를 다른 의미로 재사용하면 예전 데이터가 새 필드로 해석될 수 있습니다. 삭제한 번호는 예약해두는 편이 안전합니다.

[Protocol Buffers의 변경 규칙](https://protobuf.dev/programming-guides/proto3/)은 바이너리 형식과 JSON 형식의 호환 조건도 구분합니다. 바이너리에서 가능한 이름 변경이 JSON 표현까지 안전하다는 뜻은 아닙니다.

또한 구버전 코드가 모르는 필드를 읽고 무시할 수 있어도, 그 데이터를 다른 형식으로 변환하거나 새 객체로 다시 만들면 필드가 유실될 수 있습니다. 읽기 성공만 확인하고 끝낼 수 없는 이유입니다.

## Avro는 쓴 쪽과 읽는 쪽의 스키마를 맞춘다

Avro의 바이너리 레코드는 필드 이름이나 태그를 값마다 붙이는 방식이 아닙니다. 어떤 순서와 타입으로 썼는지 알려주는 **쓰기 스키마**가 필요합니다. 읽는 쪽은 자신의 **읽기 스키마**와 비교해서 데이터를 해석합니다.

쓰기 스키마가 데이터에 매번 통째로 붙는다는 뜻은 아닙니다. 컨테이너 파일의 헤더에 두거나, 스키마 ID로 별도 저장소에서 찾는 등의 방식으로 확보할 수 있습니다.

예전 데이터에 `nickname`이 없는데 새 읽기 스키마에 있다면 어떻게 될까요. 읽기 스키마에 적절한 기본값이 있어야 그 값을 채울 수 있습니다. 반대로 쓰기 스키마에만 있는 필드는 읽을 때 무시할 수 있습니다. 세부 조건은 [Avro의 스키마 해석 규칙](https://avro.apache.org/docs/1.12.0/specification/#schema-resolution)에 정의되어 있습니다.

이때 기본값은 데이터를 쓸 때 해당 필드를 생략해도 된다는 뜻과 다릅니다. 여기서 중요한 역할은 **읽으려는 필드가 예전 데이터에 없을 때 무엇으로 읽을지** 정하는 것입니다.

| 형식 | 필드를 해석하는 단서 | 변경할 때 확인할 것 |
| --- | --- | --- |
| JSON | 데이터 안의 이름과 애플리케이션 규칙 | 누락·추가 필드, 숫자 표현, 검증 로직 |
| Protocol Buffers / Thrift | 스키마와 필드 번호·타입 정보 | 번호 재사용, 타입 변경, 필수 여부 |
| Avro | 쓰기 스키마와 읽기 스키마의 대조 | 기본값, 이름·타입 대응, 쓰기 스키마 확보 |

## DB는 과거의 코드와 대화하는 통로다

DB에 값을 쓸 때와 읽을 때 같은 버전의 코드가 실행된다는 보장은 없습니다. 오늘 배포한 코드가 작년에 저장한 레코드를 읽을 수 있습니다.

반대 문제도 있습니다. 신버전이 `nickname`을 추가한 뒤, 구버전이 그 레코드를 읽어 자신이 아는 필드만으로 전체 문서를 덮어쓰면 `nickname`이 사라질 수 있습니다.

모르는 필드를 보존하는지, 일부 필드만 갱신하는지, 전체 객체로 다시 저장하는지까지 봐야 합니다. 데이터 형식만으로는 애플리케이션의 덮어쓰기를 막아주지 못합니다.

필드 이름을 바꾸는 예로 보면 순서가 더 분명합니다. 아래는 4장의 호환성 개념을 배포에 적용한 예시입니다.

![name 필드를 display_name으로 옮길 때 읽기 호환을 먼저 배포하고 이행 후 옛 필드를 정리하는 단계](/blog/ddia-ch04-encoding-and-evolution/schema-rollout.svg)

1. 새 코드가 `display_name`을 우선 읽되, 없으면 `name`을 읽게 합니다. 쓰기는 당분간 기존 필드를 유지합니다.
2. 이 읽기 변경이 필요한 서버에 모두 배포된 뒤, 전환 기간에는 두 필드를 함께 갱신하도록 합니다.
3. 기존 데이터를 이행합니다. 진행 중인 쓰기와 충돌하지 않게 하고, 두 필드의 값이 일치하는지도 확인합니다.
4. 구버전 서버와 관련 소비자가 더 이상 남아 있지 않고 롤백 조건도 정리되면, 옛 필드 의존과 쓰기를 제거합니다.

필드 이름 하나를 바꾸는 데도 배포가 여러 번 필요할 수 있습니다. 한 번의 코드 변경보다 공존 기간을 어떻게 넘길지가 더 중요합니다.

## RPC는 로컬 함수 호출과 다르다

서비스끼리 통신할 때도 인코딩 규칙이 필요합니다. REST는 보통 HTTP의 자원과 메서드를 중심으로 API를 구성하고, RPC는 원격의 동작을 호출하는 형태를 제공합니다. 어느 방식이든 네트워크의 실패 가능성을 없애주지는 않습니다.

로컬 함수와 달리 네트워크 요청은 서버가 처리했는데 응답만 유실될 수 있습니다. 타임아웃이 났다고 “실행되지 않았다”고 판단할 수 없습니다.

그래서 재시도할 때 같은 작업이 두 번 수행돼도 괜찮은지 확인해야 합니다. 멱등 키나 중복 처리 정책은 이 문제와 연결됩니다. 형식이 호환된다는 것과 호출이 안전하다는 것은 별도로 확인할 일입니다.

## 큐는 배포 시점과 처리 시점이 다르다

메시지 브로커는 생산자와 소비자가 동시에 실행될 필요를 줄이고, 버퍼링과 재처리에도 도움을 줍니다. 대신 메시지를 만든 코드와 소비하는 코드 사이에 시간 차이가 생깁니다.

배포를 끝냈어도 예전 메시지가 큐에 남아 있을 수 있습니다. 생산자가 먼저 바뀌면 구버전 소비자가 새 메시지를 읽고, 소비자가 먼저 바뀌면 새 코드가 예전 메시지를 읽습니다.

실패 메시지를 며칠 뒤에 재처리한다면 호환성의 범위도 그만큼 길어집니다. “현재 서버가 전부 신버전이다”만으로 옛 형식을 지워도 된다고 판단할 수 없습니다.

이 점은 메시지를 주고받는 액터 모델에도 이어집니다. 메시지로 상태를 분리하더라도, 서로 다른 버전의 액터가 공존한다면 메시지 형식의 변화는 여전히 관리해야 합니다.

## 읽고 남은 기준

스키마 변경을 볼 때 새 코드끼리 동작하는지만 확인하면 부족합니다.

- 새 코드가 기존 레코드와 대기 중인 메시지를 읽는가.
- 구버전 코드가 새 데이터의 추가 필드를 받아들이는가.
- 읽은 뒤 다시 저장해도 모르는 필드가 보존되는가.
- 필드 이름과 타입이 같아도 단위나 의미가 달라지지는 않았는가.
- 재처리와 롤백에 필요한 옛 형식은 언제까지 유지할 것인가.

4장을 읽고 나니 스키마는 현재의 데이터 모양만 설명하는 것이 아니었습니다. 서로 다른 시점에 실행되는 코드가 함께 지킬 약속이기도 했습니다.
