## 성격이 다른 일을 한 프로세스에 두면

API 서버는 요청에 빠르게 답해야 합니다. 가격 수집은 정해진 주기로 외부를 호출하는 일입니다. 둘을 같은 프로세스에 두면 일반적으로 이런 문제가 생깁니다.

- 수집 부하가 API 응답 속도에 영향을 줍니다.
- API 서버를 늘리면 수집 작업도 함께 늘어납니다.
- 배포할 때 수집까지 함께 끊깁니다.

두 번째가 특히 함정입니다. 인스턴스가 셋이면 같은 가격을 세 번 가져오게 됩니다.

## 분리와 실행 상태 관리

Solthumb에서는 가격 수집 서버를 서비스 API와 분리했습니다. 그리고 Redis로 작업 실행 상태를 관리해 중복 수집을 제한했습니다. 일반적인 형태는 짧은 락입니다.

```ts
// 구조를 설명하기 위한 예시 코드입니다.
const acquired = await redis.set(`price:${token}:running`, "1", "EX", 30, "NX");
if (!acquired) return; // 다른 작업이 이미 수집 중입니다.

try {
  await collectPrice(token);
} finally {
  await redis.del(`price:${token}:running`);
}
```

`NX`는 키가 없을 때만 저장하므로 한 작업만 통과합니다. `EX`로 만료 시간을 두면, 작업이 중간에 죽어도 락이 영원히 남지 않습니다.

## 만료 시간은 신중하게

만료가 너무 짧으면 작업이 끝나기 전에 락이 풀려 중복이 생기고, 너무 길면 죽은 작업이 다음 수집을 오래 막습니다. 작업이 보통 얼마나 걸리는지 먼저 재고 정해야 합니다.

## 정리

나눌지 말지는 코드 크기보다 **부하와 배포 주기가 같은가**로 판단하면 됩니다. 다르다면 떼어낼 이유가 충분합니다.
